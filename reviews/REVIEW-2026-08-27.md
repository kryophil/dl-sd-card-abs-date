### F-01 — Non-ASCII-Pfeil in aktivem `print()`-Aufruf (Regression des historischen Unicode-Fixes)

- **Kategorie:** 1f
- **Severity:** major
- **Datei:Zeile:** `dl-sd-card-date.py:1017-1019`

**Beobachtung:** Commit `d77f9c4` ("fix: replace non-ASCII arrows in print statements...") hat 4 print-Aufrufe mit U+2192 (→) durch ASCII `->` ersetzt, um `UnicodeEncodeError` auf Windows-CP1252-Terminals zu vermeiden. In `run_multifile()` (Funktion wurde im selben Zeitraum / im Zuge des Multifile-Features eingeführt) existiert ein weiterer print-Aufruf mit demselben Zeichen, der vom Fix nicht erfasst wurde.

**Evidenz:**
```python
1016:            if readout is None:
1017:                print(f"[WARN] Kein Auslesedatum aus '{f.name}' ableitbar und kein "
1018:                      f"READOUT_DATE gesetzt → Datei ohne absolute Zeit.",
1019:                      file=sys.stderr)
```
Gegenprobe (Grep über die gesamte Datei nach `→`): alle übrigen Treffer liegen in Docstrings oder `#`-Kommentaren (Zeilen 21, 132f., 186, 596, 795) — diese werden nie ausgegeben und sind unkritisch. Zeile 1018 ist der einzige Treffer innerhalb eines tatsächlich ausgeführten `print()`.

**Bewertung:** Dieser Codepfad wird genau dann ausgelöst, wenn im Multifile-Modus für eine Datei kein Auslesedatum aus dem Dateinamen ableitbar ist und `READOUT_DATE` nicht gesetzt ist — ein regulärer, nicht seltener Warn-Fall. Auf einem Windows-Terminal mit CP1252-Codepage (das genaue Szenario, das der ursprüngliche Fix adressierte) führt das zu einem unabgefangenen `UnicodeEncodeError`, der den gesamten Multifile-Lauf abbricht — nicht nur die Warnmeldung. Damit wird aus einer eigentlich nicht-fatalen Diagnosemeldung ein harter Absturz.

**Empfehlung:** `→` durch `->` ersetzen, wie im übrigen Code bereits umgesetzt. Da dieses Muster offenbar bereits einmal übersehen wurde, zusätzlich ein einmaliges Grep über alle print/sys.exit-f-Strings nach Zeichen außerhalb des CP1252-Bereichs, um weitere Instanzen sicher auszuschließen.

### F-02 — `_apply_config()`: gültige, aber "falsy" YAML-Werte (0, 0.0, "", False) werden stillschweigend verworfen

- **Kategorie:** 1a
- **Severity:** major
- **Datei:Zeile:** `dl-sd-card-date.py:224-231`

**Beobachtung:** Die Übernahme flacher Config-Schlüssel aus YAML in die globalen Variablen nutzt `data.get(name) or data.get(name.lower())`. Da Python `or` bei einem falsy-Wert (0, 0.0, "", False) zum rechten Operanden weiterfällt, wird ein bewusst auf `0`/`0.0`/`""` gesetzter YAML-Wert wie ein *fehlender* Wert behandelt, sobald der lowercase-Fallback-Key ebenfalls nicht existiert (Regelfall, da die YAML-Datei durchgängig UPPER-CASE-Keys verwendet, s. `dl-sd-card-date.yaml`).

**Evidenz:**
```python
213:    # Flache Schlüssel direkt übernehmen
214:    FLAT_KEYS = {
215:        "INPUT_DIR": str, "OUTPUT_DIR": str, "SD_GLOB": str, "INFLUX_GLOB": str,
216:        "J_MAX_SECONDS": float, "BIN_HOURS": float, "MIN_ANCHORS_PER_BIN": int,
217:        "N_TRIM_ITER": int, "MAX_TRIM_FRACTION": float, "MIN_ANCHORS_FOR_FIT": int,
        ...
224:    for name, cast in FLAT_KEYS.items():
225:        # Erlaube sowohl UPPER als auch lower-case Keys in YAML
226:        val = data.get(name) or data.get(name.lower())
227:        if val is not None:
228:            try:
229:                globals()[name] = cast(val)
230:            except Exception:
231:                pass
```
Beispiel-Failure: Nutzer setzt in `dl-sd-card-date.yaml` `MIN_ANCHORS_PER_BIN: 0` (bewusst, um die Bin-Mindestanzahl zu deaktivieren). `data.get("MIN_ANCHORS_PER_BIN")` liefert `0` → falsy → `or data.get("min_anchors_per_bin")` wird ausgewertet → `None` (Key existiert nicht) → `val = None` → `if val is not None` schlägt fehl → der Default (`MIN_ANCHORS_PER_BIN = 3`) bleibt aktiv, ohne jede Meldung. Gleiches gilt für `N_TRIM_ITER: 0`, `MAX_TRIM_FRACTION: 0.0`, `TIME_MARGIN_DAYS: 0.0` u.a. Dasselbe Muster (`data.get("columns") or data.get("COLUMNS")`, Zeile 234) betrifft auch `columns: []`.

**Bewertung:** Für ein laut CLAUDE.md korrektheitskritisches wissenschaftliches Tool ist eine stillschweigend ignorierte, explizit gesetzte Konfiguration ein reales Risiko — der Anwender geht von einem wirksamen Wert aus, das Skript rechnet aber mit dem Default. Dies ist strukturell dieselbe Fehlerklasse wie der historisch behobene Bug "Config-System war dead code" (Commit `3e3f423`), nur an anderer Stelle im selben Mechanismus.

**Empfehlung:** `val = data[name] if name in data else data.get(name.lower())` (oder äquivalent mit `is not None`/Schlüssel-Existenzprüfung statt `or`) verwenden.

**Aufwand:** S

### F-06 — Uneinheitliches Error-Handling: rohe Tracebacks statt `[FEHLER]`-Konvention bei kaputten Eingabedateien

- **Kategorie:** 4
- **Severity:** minor
- **Datei:Zeile:** `dl-sd-card-date.py:286-325` (`read_sd_file`), `375-416` (`read_influx_files`)

**Beobachtung:** `read_sd_file()` und `read_influx_files()` rufen `pd.read_csv(...)` und nachfolgende `.astype({...: "int64"})`/`.astype(float)`-Konvertierungen ohne umgebendes `try/except` auf. Beide Funktionen werden aus `main()`/`run_multifile()` ohne schützendes `try/except` aufgerufen.

**Evidenz:**
```python
293:    df = pd.read_csv(sd_path, header=None, encoding="utf-8-sig").dropna()
...
298:    df = df.astype({c: "int64" for c in col_names})
```
```python
1099:        sd_df = read_sd_file(sd_path)
```
(kein try/except um diesen Aufruf in `main()`)

**Bewertung:** Eine leere SD-Datei führt zu `pandas.errors.EmptyDataError`, eine SD-Datei mit Header-Zeile oder nicht-numerischen Werten zu einem `ValueError` bei `.astype("int64")` — beides propagiert als unbehandelter Python-Traceback bis zum Interpreter-Exit, im Gegensatz zu den zahlreichen anderen Stellen im selben Skript, die konsequent `sys.exit(f"[FEHLER] ...")` für vorhersehbare Fehlerfälle nutzen (z. B. Zeilen 976, 988, 1097, 1109, 1139). Für Feldeinsatz-Diagnose (nicht-technische Anwender vor Ort) ist ein roher Traceback deutlich weniger hilfreich als eine `[FEHLER]`-Zeile mit Kontext.

**Empfehlung:** An den Aufrufstellen (`main()`, `run_multifile()`) `read_sd_file`/`read_influx_files`/`read_influx_from_dir` in ein `try/except (pd.errors.ParserError, pd.errors.EmptyDataError, ValueError) as e: sys.exit(f"[FEHLER] ...: {e}")` einbetten, konsistent mit der übrigen Fehlerbehandlung im Skript.

**Aufwand:** M (mehrere Aufrufstellen: `main()` einfach + `Legacy`-Zweig + `run_multifile()`-Schleife)

### F-08 — `decentlab.py`: `tz_localize('UTC')` ist strukturell totes Fehlerbehandlungs-Konstrukt

- **Kategorie:** 6
- **Severity:** nit
- **Datei:Zeile:** `decentlab.py:107-113`

**Beobachtung:**
```python
107:    if convert_timestamp:
108:        df['time'] = pd.to_datetime(df['time'], unit='ms', utc=True)
109:        try:
110:            df['time'] = df['time'].dt.tz_localize('UTC')

Funktional unschädlich (Zeile 113 übernimmt die eigentliche Konvertierung), aber das Konstrukt ist irreführend/totes Gerüst, vermutlich ein Rest aus einer früheren Version ohne `utc=True` in Zeile 108.

**Empfehlung:** Da `decentlab.py` laut CLAUDE.md ein externes, minimal zu haltendes File ist: keine Änderung empfohlen, nur als Beobachtung festgehalten.
